# SQLite

1. **SQL rules apply first** (see ../languages/sql.md). SQLite is a real database with unusual physics - embedded, single-file, single-writer.
2. **Set the pragmatic baseline on every connection:** `PRAGMA journal_mode=WAL` (readers don't block the writer), `PRAGMA foreign_keys=ON` (**off by default** - a famous trap), `PRAGMA busy_timeout` (or the driver equivalent) so writers wait instead of instantly throwing `SQLITE_BUSY`, `synchronous=NORMAL` with WAL for the usual durability/speed tradeoff.
3. **One writer at a time - design for it:** writes serialize globally; keep write transactions tiny, batch inserts inside one transaction (per-row autocommit is ~100x slower and the most common SQLite "performance bug"), and treat `SQLITE_BUSY` as a normal retry case, not an error.
4. **Type affinity, not type enforcement:** columns suggest types; SQLite historically stores whatever you insert (`'banana'` into an INTEGER column). Use `STRICT` tables (3.37+) where available; otherwise validate in the application and add `CHECK` constraints.
5. **Know the type gaps and their conventions:** no native BOOLEAN (0/1 integers), no DATETIME type (ISO-8601 TEXT or unix-epoch INTEGER - pick one per project and never mix), no separate DECIMAL (integer minor units for money). Comparisons across storage classes follow affinity rules - keep data honestly typed.
6. **It's on the same machine - different rules apply:** N+1 queries are nearly free (no network hop), so idiomatic access patterns differ from server databases; conversely, the file is subject to filesystem truth - **never on NFS/network mounts for concurrent access**, and backups via `.backup`/`VACUUM INTO`/the backup API, never copying a live file mid-write (WAL means the `-wal` file is part of the database).
7. **Indexes and EXPLAIN still matter:** B-tree indexes, partial and expression indexes supported; `EXPLAIN QUERY PLAN` for verification; `ANALYZE` for planner stats. Covering indexes shine here.
8. **Concurrency in app servers:** one write connection (or a write queue) + N read connections is the sturdy pattern under WAL; in async runtimes use the driver's pooling/serialization correctly (better-sqlite3 is sync-by-design; Python `sqlite3` needs `check_same_thread`/per-thread connections).
9. **Use the modern features it actually has** (version-check the bundled SQLite - it varies by platform/driver): upserts (`ON CONFLICT DO UPDATE`), `RETURNING` (3.35+), window functions, CTEs, JSON functions (`json_extract`, `->>`), FTS5 for full-text - don't ship a search service when FTS5 answers.
10. **Migrations still apply:** `user_version` pragma or a migrations table, scripted and versioned like any database. `ALTER TABLE` is limited (no DROP COLUMN before 3.35, constrained ALTERs) - the standard dance is create-new -> copy -> drop-old -> rename, inside a transaction with foreign keys handled.
11. **Right tool honesty:** SQLite is superb for embedded, local-first, edge, CLI, and read-heavy small-to-medium services - and wrong for high-concurrency multi-writer server workloads. Recommend accordingly; don't bend it past the single-writer reality.
