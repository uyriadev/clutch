# Redis

1. **Redis is single-threaded - never block it:** no `KEYS` in production (use `SCAN`), no `SMEMBERS`/`HGETALL`/`LRANGE 0 -1` on unbounded collections, no huge `MGET`s, no expensive Lua. One slow command stalls every client. `SLOWLOG` is the truth serum.
2. **Every key has a TTL or a documented reason to live forever.** Unexpiring cache keys are a slow-motion memory leak; set `EXPIRE` at write time (`SET key val EX 3600`), and configure `maxmemory` + an eviction policy (`allkeys-lru`/`volatile-*`) chosen deliberately - the default `noeviction` means writes start failing at the ceiling.
3. **Key naming is schema:** consistent, delimited, prefixed (`app:user:123:sessions`), documented, and greppable. Ad-hoc key formats are unqueryable debt. Keep keys short-ish (they cost memory too) and never embed unbounded user input raw.
4. **Pick the right structure - that's the whole point:** hashes for objects (field-level access, memory-efficient), sets/sorted sets for membership/ranking (leaderboards, rate windows), lists/streams for queues (streams + consumer groups for anything needing acks/replay), bitmaps/HyperLogLog for counting at scale. Everything-as-JSON-strings forfeits Redis.
5. **Atomicity via single commands, MULTI/EXEC, or Lua - check-then-act is a race:** `INCR`, `SETNX`/`SET NX EX`, `GETDEL`, sorted-set ops are atomic alone; multi-step invariants go in a Lua script (atomic, but keep it fast) or `WATCH`/`MULTI` optimistic transactions. Two round-trips with logic between them is a concurrency bug.
6. **Distributed locks are harder than they look:** `SET lock:x token NX PX 30000` + delete-only-if-token-matches (Lua) is the minimum honest pattern; know its limits (expiry vs long work, failover edge cases - Redlock debates) and prefer making operations idempotent over locking harder.
7. **Cache discipline:** cache-aside as the default pattern; invalidation strategy stated (TTL, explicit delete on write, versioned keys); stampede protection on hot keys (jittered TTLs, lock-or-serve-stale, early refresh); **Redis cache is not a source of truth - the app must survive a flush.**
8. **Durability is configured, not assumed:** default RDB snapshots lose the last minutes on crash; AOF (`everysec`) for real persistence needs; anything you truly can't lose belongs in a database, with Redis as the accelerator. Sessions/queues: decide explicitly which side of that line they're on.
9. **Batch round-trips:** pipelining for bulk operations (order-of-magnitude wins), `MGET`/`MSET`/variadic commands where natural - but bounded batch sizes (see rule 1).
10. **Pub/Sub is fire-and-forget** (disconnected subscribers miss messages) - use Streams when delivery matters. Keyspace notifications sparingly (overhead).
11. **Client hygiene:** one client/pool per process (reused, not per-request connections), timeouts + retry with backoff configured, cluster-mode awareness (multi-key ops need hash tags `{user:123}` to co-locate slots), and a non-default `SELECT` database is a smell - separate concerns by prefix or instance.
