# MongoDB

1. **Schema design is query design:** model documents around access patterns, not entity-relationship purity. Embed what's read together (bounded one-to-few); reference what's unbounded or independently accessed. An unbounded growing array inside a document is the classic design bug (16MB cap, rewrite cost, index bloat).
2. **"Schemaless" is not "schema-free":** enforce shape somewhere - JSON Schema validation on the collection (`$jsonSchema` validator), and/or application-layer schemas (Mongoose/pydantic/typed drivers). Drifted document shapes across years of writes are the debt that kills Mongo codebases.
3. **Every query is index-backed or justified:** `explain("executionStats")` - COLLSCAN on a hot path is a defect. Compound indexes follow the ESR rule (Equality, Sort, Range) in field order; index the query, including sort direction. Unused indexes tax every write - prune with `$indexStats`.
4. **Injection exists here too:** never pass user input into query operators unchecked - `{ $gt: '' }` smuggled into a login filter is the NoSQL-injection classic. Sanitize/validate (reject `$`-prefixed keys from input), never build `$where`/server-side JS from input, cast IDs (`ObjectId`) explicitly and handle the cast failure.
5. **Updates are surgical, not read-modify-replace:** `$set`, `$inc`, `$push`/`$pull` (with `$slice` caps for bounded arrays), `$addToSet` - atomic per-document, race-free. Replacing whole documents from stale app state loses concurrent writes.
6. **Atomicity model understood:** single-document operations are atomic - design exploits that (embed data that must change together). Multi-document transactions exist (replica sets) but cost real performance - a schema that constantly needs them is a schema arguing to be redesigned (or to be in Postgres).
7. **Aggregation pipeline over app-side reassembly:** `$match` early (index use) -> `$project`/`$lookup`/`$group`/`$sort` - push computation to the server; but `$lookup`-everywhere means you built relational joins without a relational database - see rule 1.
8. **Write and read concerns are correctness settings:** `majority` write concern for anything you can't lose; read preference `secondary` accepts staleness (read-your-own-writes goes primary); retryable writes on (driver default) with idempotent operations.
9. **Pagination by range, not offset:** `_id`/indexed-field cursors (`{ _id: { $gt: last } }`) - `skip(100000)` walks everything it skips. Projections always (`{ field: 1 }`) - shipping whole documents for two fields is bandwidth and cache waste.
10. **Operational floor:** connection pooling via the driver (one client, reused), timeouts set, `maxTimeMS` on expensive queries, TTL indexes for expiring data, capped collections/change streams for their niches - and schema-version fields in documents so migrations can be lazy and explicit.
11. **Version-check features:** transactions (4.0+), time-series collections (5.0+), queryable encryption, `$lookup` improvements - verify against the deployed server and driver before using.
