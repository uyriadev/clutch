# JVM & .NET Testing - JUnit 5 / xUnit / NUnit

1. **Principles first** (see testing-principles.md). Identify the stack before writing: JUnit 5 (`@Test` from jupiter - not JUnit 4's annotations; they look alike and silently don't run under the wrong engine), xUnit vs NUnit in .NET (different lifecycle models). Match the project.
2. **Lifecycle semantics differ - know yours:** JUnit 5 creates a new test instance per test by default; xUnit does too (constructor = setup, `IDisposable` = teardown, `IClassFixture`/`ICollectionFixture` for shared expensive resources); NUnit reuses the instance (`[SetUp]`/`[TearDown]`). Static/shared state is the cross-test contamination vector in all three.
3. **Parameterize over copy-paste:** JUnit `@ParameterizedTest` (+`@CsvSource`/`@MethodSource`/`@EnumSource`), xUnit `[Theory]` + `[InlineData]`/`[MemberData]`, NUnit `[TestCase]` - with readable case names; a wall of near-identical test methods is a table asking to exist.
4. **Exception assertions capture and inspect:** `assertThrows(SpecificException.class, () -> ...)` / `Assert.Throws<SpecificException>(() => ...)` - then assert on the message/state that matters. Try/catch-with-flag is the antique antipattern; `Assert.ThrowsAsync` + await for async throws.
5. **Async tests are async all the way:** .NET test methods return `Task` (never `async void` - failures vanish), awaited properly; JVM: prefer awaiting CompletableFutures with timeouts (Awaitility for eventual conditions) over `Thread.sleep` - sleeps are the flake factory on both platforms.
6. **Assertion libraries for humane failures:** AssertJ (JVM) / FluentAssertions or Shouldly (.NET, license-permitting) over bare asserts - `assertThat(orders).extracting(Order::id).containsExactly(...)` fails with a story, `assertTrue(x.equals(y))` fails with "expected true." Assert the specific contract, not blanket deep-equality.
7. **Mock at boundaries with restraint:** Mockito / Moq-or-NSubstitute for ports you own contracts for (HTTP clients, repositories at the interface) - not your own domain logic. Prefer constructor-injected fakes; verify interactions only when the interaction *is* the contract (a sent email), not as default (over-`verify`'d tests break on every refactor). Stubbing statics/finals is a design smell before it's a mocking-library feature.
8. **Integration tests use real infrastructure via Testcontainers:** real Postgres/Kafka/Redis in containers over in-memory stand-ins (H2 and EF InMemory lie about SQL semantics) - shared container per class/collection for speed; framework slices (`@DataJpaTest`, `@WebMvcTest`, `WebApplicationFactory`) to avoid booting the world per test.
9. **Time, randomness, culture injected:** `Clock` (JVM) / `TimeProvider` or `ISystemClock` (.NET) over `Instant.now()`/`DateTime.Now` in testable code; seeded randomness; and .NET/JVM specific - culture/locale-sensitive parsing and formatting pinned (`InvariantCulture`, explicit `Locale`) so tests don't fail only on machines set to `tr-TR` or `de-DE`.
10. **Naming and structure per house convention** (`methodUnderTest_condition_expectedResult`, backtick sentences in Kotlin, `Should_...` in .NET) - pick the repo's pattern; nested classes (`@Nested`) / test collections to group behaviors; one logical behavior per test.
11. **Keep the suite honest:** `@Disabled`/`[Skip]` require a reason string and a ticket; ordered tests (`@Order`, xUnit orderers) are a last resort for true state machines, never a fix for hidden coupling; parallel execution enabled where the platform supports it - and the failures that surfaces are real bugs in the tests.
