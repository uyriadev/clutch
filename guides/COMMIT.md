# COMMIT.md - committing a session in transcript order

`scripts/transcript_commit.py` turns a finished session into a clean, ordered commit
history instead of one giant blob. It reads the Claude Code transcript (the same source
`session_report.py` uses), groups the changed files by the request that produced them,
and commits them in the order the work was done.

## The model

- Walk the transcript in order. Each genuine human request starts a new work unit; every
  file edited under it (Edit/Write/MultiEdit/NotebookEdit) is attached to that unit.
- A file is committed once, with the first unit that touched it - so commit order follows
  when each piece of work started.
- The commit message is the chapter title for that unit if one was marked, otherwise the
  request text (trimmed to a subject line). A trivial request ("continue", "yes") falls
  back to "update <files>".
- "Ready" means git currently sees the file as changed. Files the transcript touched but
  that show no diff (unchanged, reverted, or gitignored like `AI.md`) are skipped.
- Changes git sees that the transcript did not touch are left uncommitted and reported -
  the tool never sweeps unknown edits into a commit.

## Use it

```bash
python .clutch/scripts/transcript_commit.py            # print the plan (dry run)
python .clutch/scripts/transcript_commit.py --commit   # apply, in transcript order
python .clutch/scripts/transcript_commit.py --session 04ce6e3a --commit
```

Dry run is the default - nothing touches git until `--commit`. Read the plan first; if the
grouping or a message is off, either edit the plan by committing manually, or commit and
then `git rebase -i` / `git commit --amend` to adjust.

## Rules and caveats

- Messages carry NO co-author or "generated by" trailer and are ASCII-normalized
  (see `human-output.md`). They are plain developer subject lines.
- Git commits a snapshot of the current file content, not the file's intermediate state at
  that point in the session. The order and grouping reflect the transcript; the content is
  the final working-tree state. That is normal and what you want almost always.
- Run it from the project's git repo root. It refuses to run with unmerged paths.
- Pair with `session_report.py` (which explains what the session did) - this tool acts on
  the same extracted facts.

## For AI agents

When the user asks to commit finished work, prefer this over hand-crafting one commit:
run it dry first, show the plan, then `--commit`. Do not push unless asked.
