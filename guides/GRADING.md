# GRADING.md - the commit-grading rubric

This guide defines how AI-generated (or any) code gets graded. `scripts/grade.py`
embeds this rubric into every generated grading prompt. Keep it opinionated; edit it
as you learn what your projects actually need - that's the point of the system.

## How to grade

Before grading, note that a reviewer is uniquely prone to two AI failure modes from
`AI-PITFALLS.md`: **sycophancy** (softening real problems to be agreeable) and
**premature closure** (skimming the diff after the first issue). Read the whole diff,
and state problems bluntly - a wrong SHIP is the expensive mistake here.

Grade the commit(s) on each dimension below, 1-5. Anything scoring 3 or below must
come with a concrete fix (file, line, suggested change), not just a complaint.
Finish with an overall verdict: **SHIP**, **SHIP WITH FIXES**, or **REWORK**.

## Dimensions

### 1. Correctness (weight x3)
- Does the change do what the commit message claims - no more, no less?
- Edge cases: empty inputs, None/null, unicode, paths with spaces, concurrent access.
- Off-by-one, inverted conditions, swallowed exceptions, wrong default values.
- On Windows-targeted code: path separators, encoding (`utf-8` explicit?), CRLF.

### 2. Scope discipline (weight x2)
- Unrelated refactors, formatting churn, or drive-by changes bundled in? Flag them.
- Dead code, commented-out code, leftover debug prints, TODO with no ticket.

### 3. Robustness (weight x2)
- Failure modes: what happens when the file is missing, the network is down, the
  input is malformed? Errors should be caught where they can be handled, and loud
  where they can't.
- No silent `except: pass`. No bare asserts as validation in production paths.

### 4. Readability & fit (weight x1)
- Names say what things are. Functions do one thing. Matches the surrounding
  codebase's style rather than importing a new one.
- Comments explain *why* (constraints, gotchas), never *what the next line does*.
- No AI tells: casual-but-explanatory comments (not every line, not textbook),
  no co-author/"generated by" trailers in commits, standard-keyboard characters
  only (no em dashes or smart quotes). See `human-output.md`.

### 5. Security & data safety (weight x1)
- Secrets in code or logs? Injection (SQL, shell, path traversal)? Unsafe deserialization?
- Destructive operations (delete, overwrite, force-push) guarded and reversible?

### 6. Tests & verifiability (weight x1)
- Is the change covered by a test, or at least manually verifiable with a one-liner?
- If tests were changed: were they weakened to pass?

## Scoring

- **5** - exemplary, nothing to fix.
- **4** - minor nits only, none block shipping.
- **3** - at least one real issue; fixable in minutes.
- **2** - a bug or design problem that will bite; needs rework before merge.
- **1** - fundamentally wrong approach or dangerous.

Weighted total = sum(score x weight), max 50.
**SHIP** >= 45 with no dimension below 4 - **SHIP WITH FIXES** >= 35 - else **REWORK**.

## Output format the grader must follow

```markdown
## Grade: <SHIP | SHIP WITH FIXES | REWORK> (NN/50)

| Dimension | Score | Notes |
|---|---|---|
| Correctness | n/5 | ... |
| ...

### Required fixes
1. `path/file.py:123` - <problem> -> <concrete fix>

### Worth noting (non-blocking)
- ...
```
